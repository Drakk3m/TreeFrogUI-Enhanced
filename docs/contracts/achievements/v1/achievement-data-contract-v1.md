# R36SX offline achievement interchange v1

**Normative.** MUST, MUST NOT and SHOULD specify interoperability requirements for future implementations. The accepted laboratory uses its earlier isolated format. New structures in this document are proposals validated on host fixtures. Only the existing original NES laboratory on FCEUmm has physical acceptance.

## Ownership and storage

Studio owns stable game/variant associations, authoring, metadata, authorized definitions and the canonical PC ledger in its existing versioned SQLite database. PicoArch owns content verification, memory access, evaluation, unlock persistence, and the in-game notification and chime. rcheevos owns condition semantics. FrogUI owns presentation and reads verified durable snapshots with no gameplay evaluation. The SD is the offline medium; after gameplay PicoArch owns newly earned local progress. Studio export must not write device progress. No gameplay Internet dependency, audio driver change or new console storage engine is part of this contract.

All new paths below are relative to cubegm/enhanced/ra. Existing rom_identity.json, profile.json, avatar.png, cache/<console_id>/<ra_hash>/gamepack.json, badges/ and local/r36sx-lab/ retain their existing readers, write rules and meanings.

| Path | Versioned document or asset | Writer |
| --- | --- | --- |
| identities/v1/{game_id}/{content_key}.json | One path association per exact variant and stable game | Studio |
| metadata/v1/{game_id}/{namespace}/{set_id}/{revision}.json | Optional presentation for the set | Studio |
| definitions/v1/{namespace}/{set_id}/{revision}/{content_key}.json | Executable conditions and identity | Studio |
| assets/v1/{sha256}.png | Content-addressed avatar or badge | Studio |
| players/v1/{profile_id}.json | Stable local player | Studio |
| players/v1/selected.json | Active offline profile | Studio initially; device selection may be added with the same atomic writer protocol |
| capabilities/v1/{core_sha256}.json | Evidence-qualified capability record | Runtime/build tooling. Studio may mirror verified records byte-for-byte |
| progress/v1/{profile_id}/{scope_key}/{a,b}.json | Alternating snapshots | PicoArch |

Curly-brace values are validated components. revision is decimal without leading zeroes. content_key and scope_key are digests of the canonical content and scope objects. JSON documents are envelopes with kind, version and payload. Definition/progress envelopes add sha256. Other documents have no envelope checksum. SHA-256 uses lowercase hexadecimal. Canonical bytes are UTF-8 without BOM, object keys in unsigned UTF-8 order, no whitespace, NFC Unicode scalar strings, minimal decimal integer syntax, lowercase literals, no escaping beyond quotation marks and backslashes within the allowed strings, and arrays in supplied order. All schema keys are ASCII. No floats, negative zero, leading zeroes, duplicate keys, control characters, noncharacters U+FFFE/U+FFFF, or surrogate code points. The envelope digest covers canonical payload bytes only. Reformatting is harmless and changing any payload value changes the digest. This checksum detects corruption and binds revisions. It does not prove authenticity, authorization or anti-tamper protection.

## RA-C01 · Content identity

The exact identity tuple is (console_id, method, sha256). The numeric console uses the rcheevos console registry. Studio game_id is a UUIDv4 persistent across path edits and may map to multiple exact variants. platform and rom_path are required discovery values with distinct semantics. In a generalized v1 identity, platform is the stable canonical platform key, derived from Studio's audited logical key in lowercase ASCII. Its value is fc for NES, sfc for SNES, and md for Mega Drive. It must not vary when the same game moves between launchers. rom_path is the exact SD-relative locator, including the launcher's physical folder. Neither duplicate canonical platform fields nor core identity in platform are permitted. The schema representation remains v1; this is a semantic clarification and more precise validation of existing fields.

The legacy public identity platform value is an association token, preserving both old logical identifiers (FC, SFC, MD) and verified launcher aliases (nes, snes, sega). Do not reinterpret the field as a core selector or rewrite old records automatically. For new legacy TreeFrogUI exports Studio should emit the actual final folder token, preserving its spelling, after resolving the canonical platform. This gives immediate compatibility with the exact-string reader where the existing console/hash/path checks also pass. Enhanced must accept either form through the common binding rule below, including old exports which cannot already be read by the accepted binary.

Resolve the exact ROM locator first. An exact roms/<folder>/ prefix denotes TreeFrogUI; a known first-level platform folder denotes CubeGM. Derive the physical platform from the appropriate launcher mapping and normalize the declared token independently with ASCII case-folding (no fuzzy names). Both must resolve uniquely to the same canonical key. Verify the supplied rcheevos console ID also matches that key and any approved content/console mapping. Then retain the reader's exact locator, size/mtime for public display, and pack console/game/RA hash cross-checks. Do not use case folding to weaken the exact locator or trust it for content. For execution validate independent SHA-256 and exact installed core/provider. Reject unknown tokens, ambiguous grouped aliases, unregistered console/variant bindings, path/console mismatches and actual content mismatches. Leave ordinary launch and public artwork independent of failures. Source-backed mappings and unresolved routes appear in schemas/platform-mapping-v1.json; its inventory alone grants no runtime compatibility. RA game ID and optional RA-compatible MD5 identify public metadata only. File size and mtime, when used by the legacy reader or PC cache, are hints. A whole-archive SHA-256 is advisory and must never identify an inner ROM executable.

raw-sha256-v1 hashes the bytes delivered to the core, including any header the loader retains. For an archive hash its effective extracted, selected member after patches. The optional archive_member is an exact normalized relative member name. Reject ambiguous members, unsafe paths and unsupported decompression. Container renames and repacking keep the identity when loaded bytes are the same. A patch or variant that changes the effective bytes creates a different identity until a definition explicitly lists that variant through its own package. A slot per exact content variant means no wildcard. Studio can update locators without rewriting progress. FrogUI uses identity indexes to present candidate data without rehashing the library in the draw loop; display a pending/unverified association until a trusted scan or runtime result establishes it.

fileset-sha256-v1 hashes the canonical array of objects containing role and sha256, in the same order as identity.components. Each component digest is SHA-256 of that exact member's bytes. Paths are locators and excluded. A loader adapter MUST establish the complete dependency order deterministically and include controlling descriptor bytes such as CUE/M3U and all tracks/discs; roles are adapter-defined registered lowercase keys and unique in the array. No duplicate paths. Within that version, moving the whole tree without changing loaded bytes retains identity. Editing a descriptor, changing track order or substituting a member changes identity. For disc swaps, verify the full declared set before activation, allow only verified members, and reset transient state on a switch. If any dependency, transform, loader ordering or memory equivalence is uncertain, mark unavailable. No fileset adapter is registered or enabled in the first implementation, and its execution gate remains closed. The host fixture verifier only implements raw, unarchived content.

PicoArch must verify the exact buffer if supplied. For full-path cores, resolve the final effective path, including patched/extracted temporary content. Hash a stable read-only path controlled by the loader and ensure the core opens that same verified snapshot. A core that can reopen mutable, ambiguous content without a verifiable handoff is unavailable. Use bounded streaming and stop on identity mismatch. A strong hash over the real loaded content takes priority over Studio locators or cached observations. Hash at launch and on relevant content changes, never in the frame loop.

## RA-C02 · Metadata and namespaces

Each set identity is (namespace, set_id, revision). Each achievement joins by a unique id within that set revision. diagnostic.* never influences normal or official counts. local.* is Studio-managed original/authorized local content. ra.* reserves official-associated metadata and requires a separate authorization policy before any executable use. Namespace allocation for independent creators is a Studio policy; a v1 Studio must reject collisions rather than overwrite. Local sets never fabricate service IDs. The existing public RA-02.1 reader stays independent and metadata-only in meaning. Its definition_fingerprint_md5 is advisory metadata. Aliasing it into a condition is invalid.

Local metadata gives titles, descriptions, points and optional badge digest. A content-addressed PNG can serve multiple roles within the respective geometry limit. Missing metadata is a presentation fallback to the stable ID, blank description, generic badge and unavailable points. Missing/corrupt assets use a generic badge without affecting activation or launch. For a set with both metadata and definitions, the ID sets must agree. A broken metadata package is quarantined as an optional presentation failure. A metadata-only game remains browsable with unavailable runtime status. Metadata must never contain executable fields. The reference package validator rejects inconsistent bundles so Studio can repair them before Apply.

## RA-C03 · Executable definitions

A definition envelope binds exactly one game, set revision, console and exact content identity. It contains the complete rcheevos condition string per ID, a named memory provider, required feature keys and provenance/license. Duplicate IDs, unknown major version, bad digest or conditions, mismatched actual content, unsupported features/addresses and unsupported provider all disable that whole package. No partial activation in v1. A matching definition may activate with missing metadata using fallback title and badge. No alternate interpreter, scripts, binaries, shell operations, dynamic code loading or arbitrary file callbacks. The host cap fixture uses a restricted admitted subset of real rcheevos syntax. Other syntax remains an explicit future capability, never implicitly enabled. Provenance is a policy input, not a trusted assertion from a checksum.

Two installed definitions claiming the same namespace/set/revision/content with different payloads are a conflict. Higher revision for the exact content is selected only when valid; if a higher recognized revision is present but invalid, mark unavailable and expose the error instead of silently activating an older ruleset. Never select between distinct namespaces by sort order. The launch configuration must explicitly select a set if more than one valid set exists for the same verified content. The first implementation rejects ambiguous sets until a selection UI/settings contract exists. Studio creates a new revision for condition or ID-set changes and retains the old snapshot/history. An identical achievement ID across revisions is not evidence of equivalence. Never transfer unlocks automatically for edits/removals. Historic revisions remain importable.

## RA-C04 · Progress and crash handling

Scope is (profile UUID, namespace, set ID, revision, exact content identity, definition payload SHA-256). The stable event ID is SHA-256 of canonical {"achievement_id": ID, "scope": scope}. Event identity is independent of path, timestamps, SD card and import generation. It is an idempotency key, not a signature. The record state is unlocked and verification local-runtime. A trustworthy clock allows UTC Unix seconds with timestamp_status trusted. A clock with no independent trust has timestamp_status unknown and omits unlocked_at. A bad or missing RTC must not block saving. Core checksum is optional advisory provenance.

The v1 store is bounded canonical JSON snapshots, two slots per scope, at most 128 records per slot. Use one device writer per scope. Order records by binary ASCII achievement_id when writing. Start with a valid empty generation-0 snapshot when the exact local scope is initialized. Recover by independently validating both slots, including scope, digest and event IDs, and union valid unlocks. The highest valid generation controls the next write. Same-generation conflicts with different event sets are recovered by union and reported. To reconcile duplicate IDs with different provenance, retain the earliest trusted timestamp, if any, then the lexicographically smallest canonical event as deterministic tie-break. Counts are independent of this auxiliary choice. Rewriting or importing older snapshots never subtracts records. On generation overflow stop and ask for explicit maintenance, never wrap.

Copy the union plus the new verified unlock to a unique exclusive temporary same-directory regular file. Flush file contents, close it, atomically rename over the older or invalid slot, then fsync the directory. Fail closed before replacing a good snapshot if directory sync is known unsupported. Do not mark that event durable in the current live session until the final sync succeeds. If failure occurs after rename, durability is uncertain until independent remount/recovery validates it. FAT and surprise unplugging are outside a strong fsync guarantee. Recovery only considers the two complete named slots, ignores temporary files, keeps the older good slot and reports corruption. If neither is valid, the scope is unknown. Studio can quarantine valid-looking orphan records without marking them official or enabled. Writes are event-driven and should run on a bounded worker; any event queued but unsaved remains tentative and must be surfaced as such. Avoid blocking on every frame. No per-frame disk reads, parsing, decoding or hashing. Prefer JSON to compact binary because the payload is bounded and host tools need no bespoke decoder. Reject a single unbounded journal because truncation, compaction and scan require additional protocols. Two JSON slots trade small write amplification for an independently readable recovery point.

A scope with an authoritative valid snapshot and resolved set can show absent events as locked locally. Missing, corrupt or unresolved evidence is unknown, especially for public metadata. Official verification is supplied only by an independently authorized Studio/provider record, never by the local snapshot. When Studio can establish exact service achievement equivalence, show local and official indicators on one logical item, count once and count points separately. Without that independent link keep counts visibly distinct. Diagnostic totals are an explicitly separate view. The physically accepted legacy laboratory HUD remains unchanged until migration approval.

## RA-C05 · Profiles

Studio assigns a random UUIDv4 independently of username/avatar. Reuse the same UUID on multiple SDs for the same player only via deliberate association. Profile selection is a pointer to an installed UUID, latched at game launch. Changes take effect next launch. If selection is missing or references no profile, show metadata and allow gameplay without activation for local progress. Names and avatar digests are presentation only. An optional RA username in the local profile is unverified contact/display information. An externally verified association lives in Studio's authorized account model, separate from SD. No credentials or tokens on SD. Import unknown profile UUIDs to a quarantine record keyed by UUID; offer explicit link/creation and never match by text. Legacy local-player is a special typed diagnostic association, not the new UUID namespace. Migration requires an explicit user export or choice.

## RA-C06 · Runtime capability and lifecycle

Capability files are observations from a build-verified, explicit provider registry, never permission granted by removable media. They describe exact core checksum/ID, console, memory regions, feature keys, accepted definition versions and rcheevos revision. Runtime selects only its own verified provider. Core selection remains the launcher's existing responsibility and is resolved with exact per-ROM override, folder override, native folder default and extension fallback in that order for FrogUI's NES launch route. Do not infer core equivalence from normalized platform or a capability file. For the first generalized NES test use the physically accepted FCEUmm digest, delivered through the existing explicit per-ROM override for roms/nes or through the existing roms/FC default. Unknown or conflicting selection leaves RA unavailable while the ROM remains playable. Runtime rechecks geometry and live bounds and preserves failures as per-session status. Independent facts to surface: metadata present, definition present, definition validated, ROM verified, core supported, provider compatible, runtime active/unavailable with reason, and local progress valid/unknown. No capability document alone proves activation. The FCEUmm reference record is physical-legacy-only and generalized_enabled false. The original NES lab is the only accepted physical reference. No completion claims for other cores or systems.

Flow: catalog metadata → discover definitions and capabilities → launch → verify actual bytes → confirm core and memory → activate → evaluate after forward retro_run → detect and deduplicate unlock → attempt persistence → announce durable or transient event according to outcome → refresh gallery and Home with validated scope → import into Studio. The existing gallery and popup remain the one presentation path. Unknown states need neutral graphics. Locked shows grayscale, verified local unlock color and local status, and independent verified official status only when received. Rejecting RA leaves the game playable. Counter counts distinct logical achievements from verified records, never rows written by UI. On settings/launch transitions do a bounded refresh at return/start, not per-frame.

Durable progress is outside emulator save states and rewind. Reset or successful deserialize clears transient conditions and resets readiness; Quick Resume follows deserialize. No evaluation during rewind frames. Fast-forward evaluates each forward emulated frame once regardless of video presentation and queues notifications bounded by time, not render count. A failed state load should preserve or safely reinitialize the current runtime only per adapter; never touch durable records. On shutdown drain bounded pending persistence or explicitly report unsaved events and destroy runtime state. Duplicate suppression is within exact immutable scopes. These are local soft-mode semantics, with no Hardcore or retroactive official submission claim.

## RA-C07 · Export, import and versioning

Review Changes must preview profiles, paths, assets and definition provenance. Apply installs immutable metadata/definitions/assets via staged validated writes, then publishes identity/profile locators last using atomic replacement. Write each rename and flush under the corresponding ownership rule. Old and new files may coexist safely by revision; failed Apply leaves old referenced items readable, and orphans may be cleaned after a later successful Apply. Updating a path is reversible. Do not remove progress, reuse old scope for changed bytes, or restore an older PC progress snapshot during normal export. A game removal detaches library association while retaining imported progress and its identity. Never couple progress retention to catalog deletion. Revisions are immutable and path relocations atomic.

Import validates envelope, scope, event IDs and definition association and inserts by unique event identity in one existing SQLite transaction. Duplicate imports from either SD are a union. Missing definition, unknown game/profile or removed game leaves a retained unresolved row for later reconciliation. No ROM file has to be copied into the PC database. Malformed rows are reported independently. Import of an older SD does not erase local rows. Reset is a separately confirmed operation restricted to (profile, namespace, set, revision, ROM), with an explicit card-only versus PC-history distinction. A card-only reset removes both slots of that scope after backing them up; historical imports remain on PC and normal exports do not restore them. A coordinated reset across cards is out of v1; another card's old records may still be imported under the same event IDs. Ask for an explicit history policy before removing imported history. Cross-device synchronization and official submission are outside v1.

Unknown major versions fail closed per artifact and leave gameplay independent. Changes that require new fields, semantics, canonical digests or storage rules use a new major path/envelope. V1 is closed-shape; new semantic fields require a new major, while new fixtures, explanations and registered capability values with unknown capabilities rejected may be released as a pinned Git revision. Each consumer can adopt a new contract commit independently and must test its reader against the published fixtures.
